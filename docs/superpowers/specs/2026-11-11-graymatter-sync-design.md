# GrayMatter — работа с локальной копией и синхронизация: дизайн

Дата: 2026-11-11
Статус: схема согласована с владельцем в чате 2026-11-11.

Пометка **[решение Claude]** — выбор, который сделал Claude, а не владелец. Владелец может его оспорить. Всё остальное решено владельцем в обсуждении.

Основная спека: `docs/superpowers/specs/2026-11-10-graymatter-revival-design.md`. Эта спека меняет только то, как приложение получает данные из базы. Модель данных и команды остаются прежними.

## 1. Зачем

Сейчас после каждой успешной записи приложение заново скачивает весь текущий инвентарь (`packages/app/app/lib/workspace.ts`, функция `write()`, ветка `loadCurrent()`).

- **Размер.** Снимок весит ~1,2 КБ на предмет при передаче. Это замер на синтетических данных: ~1 вариант, ~1,5 атрибута и 1 фото на предмет. Neon по HTTP ответы не сжимает (проверено для `gzip`, `br` и `zstd`).
- **Трафик.** Первичный ввод 2 000 предметов по две записи на предмет — это ~4,6 ГБ, почти все 5 ГБ месячного исходящего трафика Neon Free. При превышении база отключается до конца месяца.
- **Скорость.** Каждое сохранение ждёт эту загрузку: 1–3 с на LTE. Всё это время кнопки приложения серые.
- **Второй, мелкий перерасход.** После своей записи забывается известная ревизия, и следующее обновление скачивает снимок ещё раз.

Модель владельца: инвентарь — это не API, к которому ходят за каждым экраном. Это **локальная копия**, которую синхронизируют раз в период или по запросу.

## 2. Цели, не-цели, анти-цели

### Цели
1. **Обычная запись без полной загрузки.** Запись — это один запрос. В ответе приходят изменённые строки, они применяются к локальной копии.
2. **Дешёвая синхронизация по кнопке.** Пункт «Sync» в меню инвентаря проверяет ревизию базы. Полная загрузка только если база изменилась. Нажимать можно сколько угодно.
3. **Полная перезагрузка по кнопке.** В настройках источника есть «Reload everything»: полная загрузка без сравнения ревизий.
4. **Автоматическая проверка ревизии** — при запуске, при появлении сети и при обращении к данным, если прошёл интервал. Интервал задаётся в настройках.
5. **Трафик.**
   - Первичный ввод 2 000 предметов (≈4 000 записей) — не больше ~50 МБ.
   - Обычный месяц (1–3 тыс. предметов, ~20 записей в день) — десятки мегабайт.

### Не-цели
- Живые обновления с других устройств: push, websocket, опрос по таймеру.
- Очередь записей без сети. Это остаётся не-целью основной спеки.
- Пересчёт команды на телефоне (редьюсер на TypeScript).
- Ревизия на каждый инвентарь в схеме базы. Ревизия остаётся одна на источник.
- Счётчик трафика в интерфейсе.
- Подключение одним запросом (П1, задача 8 ночного обзора) — отдельно.
- Остальные предложения плана 6 из ночного обзора (П2–П4) — отдельные планы.

### Анти-цели
- **Тихое расхождение.** Локальная копия отличается от базы, а приложение считает, что она актуальна.
- **Потеря или задвоение своей записи в копии.** Запись подтверждена базой, но в копии её нет, или она применена дважды.
- **Полная загрузка после обычной записи.**
- **Синхронизация что-то пишет в базу.** Она только читает.

## 3. Как работает — решения владельца

### 3.1 Экран работает с локальной копией
Всё, что видно на экране, берётся из локальной копии текущего инвентаря: память плюс IndexedDB, как сейчас. Полная загрузка инвентаря бывает только:
- по кнопке «Sync», если ревизия изменилась;
- по кнопке «Reload everything»;
- при автоматической проверке, если ревизия изменилась;
- при первом открытии инвентаря, копии которого на устройстве нет.

### 3.2 Запись
- Команда уходит в базу.
- База в той же транзакции возвращает актуальное состояние всего, чего коснулась команда, и ревизию источника до и после записи.
- После подтверждения приложение применяет это к локальной копии.

### 3.3 «Sync» в меню инвентаря
Новый пункт в меню переключателя инвентаря (`InventorySwitcher.vue`), рядом с «Rename» и «Archive».
- Приложение читает список инвентарей источника вместе с ревизией (`listInventories`, сотни байт).
- Ревизия совпала с ревизией копии — больше ничего не загружается.
- Не совпала — текущий инвентарь загружается заново.
- Список инвентарей обновляется в любом случае. Новый инвентарь, созданный на другом устройстве, появится после «Sync».

### 3.4 «Reload everything» в настройках источника
- Ревизии не сравниваются: заново загружаются список инвентарей источника и текущий инвентарь, если он из этого источника.
- Сохранённые копии остальных инвентарей этого источника считаются устаревшими. Они загрузятся целиком при открытии.
- Назначение — на случай, если копия на устройстве испорчена или выглядит неправильно.

### 3.5 Автоматическая проверка и интервал
- Это не периодическая задача и не таймер.
- Проверка «пора ли» стоит в общем входе, через который идут обращения к данным. Если интервал истёк, выполняется то же, что делает «Sync».
- Интервал — настройка устройства.

### 3.6 Изменения с другого устройства
Владелец поменял что-то на другом устройстве — он нажмёт «Sync». До этого или до истечения интервала устройство может показывать старое. Это нормально.

## 4. Решения Claude

### 4.1 Что именно применяется к копии **[решение Claude]**
- Применяются **строки, прочитанные базой в той же транзакции после записи**. Телефон не пересчитывает команду сам.
- **Почему.** Остатки, суммы и последняя цена (`StockLine`) считаются SQL-агрегатом по движениям. Копия этой логики на TypeScript рано или поздно разойдётся с базой. Чтение после записи совпадает с полной загрузкой по построению, если использовать те же запросы с фильтром.
- **Граница затронутого — «срез предмета».** Для каждого предмета, которого коснулась команда, приходят все его строки: предмет с тегами, варианты, значения атрибутов предмета и вариантов, фото, строки запаса. Они целиком заменяют срез этого предмета в копии. Если предмета в ответе нет (его удалили, в том числе с другого устройства), он удаляется из копии.
- **Маленькие таблицы** (строка инвентаря, папки, теги, атрибуты, единицы) перечитываются целиком, если команда их коснулась. Они маленькие.
- **Редкие широкие команды** обновляют копию полной загрузкой текущего инвентаря. Это:
  - `restore`;
  - `archive` и `deletePermanently` папки;
  - `deletePermanently` инвентаря;
  - `tag.delete`, `attribute.delete`, `unit.delete` — каскады по многим предметам.

  Строитель может сократить этот список, если для команды это дёшево и покрыто тестом из 4.6.
- Команды, которые меняют список инвентарей (создание, переименование, архив инвентаря), как и сейчас, перечитывают список. Это сотни байт.

### 4.2 Правила ревизии **[решение Claude]**
У копии есть «известная ревизия» — ревизия источника, при которой копия заведомо полна.

- **Атомарность «ревизии до».** Пакет записи сначала блокирует строку ревизии (`gm_meta`, `key = 'rev'`, `for update`) и читает «ревизию до», и только потом пишет. Записи идут обычными транзакциями (READ COMMITTED), а подъём ревизии сейчас стоит последним. Без блокировки чужая запись может закоммититься между нашими инструкциями и остаться незамеченной — это и есть тихое расхождение. С блокировкой все записи в источник выстраиваются в очередь на этой строке.
- **Полная загрузка** возвращает ревизию, прочитанную в той же транзакции, что и снимок. Сейчас ревизия берётся из более раннего `listInventories`.
- **Своя запись**, где «ревизия до» равна известной ревизии: между нашими загрузками никто не писал. Строки применяются, известная ревизия становится «ревизией после». Следующий «Sync» ничего не загружает.
- **Своя запись**, где «ревизия до» отличается от известной: кто-то писал между нашими обращениями.
  - Строки всё равно применяются.
  - Копия помечается устаревшей: известная ревизия становится неизвестной.
  - Следующий «Sync» или проверка по интервалу загрузит инвентарь целиком. Ровно одна полная загрузка, а не после каждой записи.
- **Копии других инвентарей** того же источника. Своя запись в инвентаре A, где «ревизия до» равна известной ревизии источника, не делает устаревшими сохранённые копии инвентарей B и C. Между этими ревизиями изменилась только эта запись, а она касалась A. Как именно двигать их ревизии, решает строитель.
- **Исход записи неизвестен** (таймаут, обрыв): копия помечается устаревшей. Если команда на самом деле прошла, следующая проверка это увидит. Повтор той же команды идемпотентен и тоже вернёт строки.
- **База отклонила запись** (ошибка ограничения, `failed`): сразу выполняется «Sync». Копия заведомо расходится с базой.
- **Проверка до отправки.** `validateCommand` по-прежнему проверяет команду по локальной копии. Если копия устарела, проверка может отклонить законную команду. Это не страшно: «Sync» исправит копию.

### 4.3 Где стоит проверка «пора ли» **[решение Claude]**
Проверка вызывается:
- при запуске приложения. Подключение к источнику и так читает список с ревизией, так что запуск сам по себе считается проверкой;
- при появлении сети (`online`) — как сейчас;
- при возвращении в приложение (`visibilitychange`). Сейчас это `refreshIfStale` с жёсткими 15 минутами, станет настройка;
- перед записью;
- перед загрузкой журнала предмета (`loadMovements`).

Если интервал не истёк, сети не будет никакой, кроме самой записи или чтения журнала.

**Отсчёт интервала** ведётся от последней успешной проверки любым путём, включая кнопку.
- Своя запись, где «ревизия до» совпала с известной, тоже считается проверкой: она доказывает, что никто другой не писал.
- Запись, где ревизия не совпала, отсчёт **не** сбрасывает. Иначе устаревшая копия не загрузилась бы сама, пока вы продолжаете вносить данные.

**Неисправный источник.** Интервал и «Never» относятся только к проверкам исправного источника. Если текущий источник в состоянии `unreachable` или `error`, при возвращении в приложение он, как и сейчас, пробуется сразу. Другой неисправный источник — не чаще раза в `FAILED_RETRY_MS`.

**Что охватывает «Sync».** Обновляются списки инвентарей всех источников: это проверка ревизии каждого. Текущий инвентарь загружается заново, только если изменилась ревизия его источника. Автоматическая проверка по интервалу делает то же самое.

### 4.4 Интервал **[решение Claude]**
- Варианты: 5 мин, **15 мин (по умолчанию, как сейчас)**, 1 ч, 6 ч, сутки, «Never».
- «Never» отключает только проверку по времени. Запуск, появление сети и обе кнопки по-прежнему проверяют.
- Хранится в настройках устройства (`DeviceSettings` в IndexedDB) и действует на все источники.

### 4.5 Интерфейс **[решение Claude]**
Интерфейс приложения английский (`packages/app/i18n/locales/en.json`).
- **Меню инвентаря.**
  - Пункт «Sync», под ним мелко «Checked 5 min ago» (относительное время последней успешной проверки).
  - Во время проверки — индикатор на пункте.
  - Результат — тост: «Up to date» или «Updated». При ошибке — существующие сообщения о недоступности источника.
- **Настройки, общий раздел.** Выбор «Check for changes»: «Every 5 min», «Every 15 min», «Every hour», «Every 6 hours», «Once a day», «Never».
- **Настройки, действия источника** — рядом с экспортом копии на экране Settings.
  - Кнопка «Reload everything» с подсказкой «Downloads this source's data again. Use it if something looks wrong.»
  - Результат — тост «Reloaded».
  - Подтверждение не нужно: действие ничего не удаляет.
- Существующий статус «updating» в `AppStatus.vue` остаётся для загрузок.

### 4.6 Страховка от расхождения **[решение Claude]**
- **Свойство-тест на PGlite** (dev-зависимость `fast-check`). Для случайной последовательности команд после каждого шага сравниваются копия до шага с применённым ответом записи и свежая полная загрузка. Они должны быть равны.
  - Сравнение без учёта порядка строк в массивах: интерфейс сортирует сам (`lib/views.ts`, `lib/item-view.ts`).
  - Строитель проверяет, что ни одно место интерфейса не опирается на порядок из SQL.
- Без зелёного теста применение строк к копии не включается.
- В тесте участвуют и команды «другого устройства» между своими. Проверяется, что копия помечается устаревшей, а после проверки ревизии загружается ровно один раз.
- **Conformance на Neon** (HTTP и WebSocket, под `GM_NEON_TEST_URL`): пакет записи возвращает прочитанные строки, и «ревизия до» и «после» читаются атомарно с записью.

### 4.7 Сохранение копии на устройстве **[решение Claude]**
- После применения строк копия пишется в IndexedDB не чаще раза в 2 с и обязательно при уходе приложения в фон (`visibilitychange: hidden`).
- Применение строк создаёт новый объект снимка: `views.ts` кеширует индексы в `WeakMap` по объекту снимка.

## 5. Ограничения
- **Neon Free:** 5 ГБ исходящего трафика и 100 CU-ч в месяц. Ответы по HTTP не сжимаются.
- **Три реализации исполнителя** — PGlite (демо в dev и тесты), Neon HTTP, Neon WebSocket. Все три должны уметь вернуть строки чтений из пакета записи. Запись и чтения — одна атомарная транзакция.
- **Идемпотентность сохраняется.** Повтор команды, чьи вставки `on conflict do nothing`, ничего не меняет, но поднимает ревизию и возвращает строки.
- **Ревизия непрозрачна:** это UUID, сравнивается только на равенство. Её поднимает каждая запись и каждая миграция.
- **Строки подключения и ключи** не попадают в логи, тексты ошибок и тесты.
- **Тестовая база** — только по `GM_NEON_TEST_URL` из `.env.local`, имя заканчивается на `_test`. `neondb` тесты не трогают.
- **Существующее поведение сохраняется:** статусы `read_only`, `newer`, `unreachable` и `error`, демо-источник, кеш на устройстве, экспорт копии.

## 6. Приёмка
1. 20 подряд `stock.receive` → 0 вызовов `loadInventory`.
2. Быстрое добавление с фото (`item.create` + `photo.add`) → 0 вызовов `loadInventory`.
3. «Sync» при неизменной базе → один `listInventories`, 0 `loadInventory`. Так же после серии своих записей.
4. Другое устройство записало, затем «Sync» → ровно один `loadInventory`, изменение видно.
5. Чужая запись между двумя своими → строки обеих своих записей в копии, копия помечена устаревшей. Следующий «Sync» → ровно один `loadInventory`.
6. «Reload everything» → `loadInventory` независимо от ревизии. Копии других инвентарей источника загружаются при открытии.
7. Своя запись в инвентаре A, затем переключение на B (копия на устройстве, никто другой не писал) → 0 `loadInventory`.
8. Источник исправен. Возвращение в приложение раньше интервала → 0 сетевых запросов. После интервала → одна проверка ревизии.
9. Источник исправен, выбран «Never» → при возвращении в приложение сети нет. «Sync» работает.
10. Своя запись с несовпавшей «ревизией до» не сбрасывает отсчёт интервала. Своя запись с совпавшей — сбрасывает.
11. Свойство-тест: 200 последовательностей зелёные. Conformance на Neon зелёный.
12. Имитация первичного ввода 2 000 предметов по 2 записи → 0 `loadInventory`. Суммарный размер ответов записи ≤ 50 МБ (на PGlite меряется как размер JSON результатов).
