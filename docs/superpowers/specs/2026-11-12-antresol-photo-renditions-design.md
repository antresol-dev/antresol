# Antresol — копии фото и хранилище ImgBB: дизайн

Дата: 2026-11-12
Статус: форма согласована с владельцем в чате 2026-11-12 («выглядит ок, давай делать»).

Пометка **[решение Claude]** — выбор Claude, владелец может его оспорить. Всё остальное решено владельцем.

## 1. Зачем

**Почему ImgBB.** Imgur с конца 2025 года не регистрирует новые приложения для API и скрыт из выбора хранилищ (`d1a8350`). Cloudflare R2 владелец отклонил: он просит карту даже на бесплатном тарифе. Для фото деталей и домашних вещей владельца устраивает хранилище, где фото открыто по ссылке. Поэтому третьим хранилищем рядом с Uploadcare и Cloudinary становится **ImgBB**.

**Почему нужен набор копий.** ImgBB не уменьшает фото по ссылке, в отличие от Uploadcare, Cloudinary и Imgur. Вместо этого при загрузке он один раз отдаёт адреса готовых копий. Если их не сохранить сразу, потом их уже не вернуть. Поэтому у фото появляется **набор копий** (`urls`). Его форма общая, чтобы им могли пользоваться и будущие хостинги.

**Что ImgBB делает на самом деле.** Проверено одной загрузкой 2026-11-12: WebP 2048×1536, 192 КБ, `expiration=600`.
- Оригинал возвращается байт в байт: WebP 2048×1536.
- `medium` — WebP, вписан в 640 px с сохранением пропорций: получилось 640×480, 18 КБ.
- `thumb` — WebP, обрезан в квадрат 180×180, 5 КБ.
- API и `i.ibb.co` отдают `Access-Control-Allow-Origin: *` и `Cache-Control: max-age=315360000`.
- `i.ibb.co` отдаёт ту же картинку, если к адресу дописать `?antresol=thumb`.
- Ширину и высоту ответ сообщает только для оригинала.
- Имя загруженного файла становится публичным заголовком картинки.

## 2. Данные фото

### Копия (`Rendition`)

```ts
interface Rendition {
  url: string                 // https-адрес копии
  role: string                // название копии у хостинга: 'original', 'medium', 'thumb', …; только для справки
  width: number               // размер копии в пикселях
  height: number
  fit: 'inside' | 'cover'     // inside — пропорции сохранены; cover — обрезана ровно в width×height
  type: string | null         // MIME, если хостинг его сообщил
}
```

### Новые поля фото

Все четыре поля могут быть `null`.

| Поле | Колонка | Что хранит |
|---|---|---|
| `urls: Rendition[] \| null` | `urls jsonb` | Все копии, которые вернул хостинг, включая оригинал. У Uploadcare, Cloudinary и Imgur пусто (`null`): они уменьшают фото по ссылке. |
| `width`, `height: number \| null` | `width integer`, `height integer` | Размер загруженного файла, то есть того, что лежит по `url`. Записывается у всех хранилищ: приложение само сжимает фото и знает размер точно. |
| `deleteHandle: string \| null` | `delete_handle text` | Ключ удаления на хостинге: `delete_url` у ImgBB. Сейчас только хранится. |

**`url` по-прежнему оригинал.** На него приложение откатывается всегда. `file_id` — номер файла у хостинга (у ImgBB это `data.id`).

**Кто может удалить фото по `deleteHandle`.** Любой, у кого есть строка подключения к базе или файл резервной копии. Такой человек и так может стереть всю базу; владелец согласен.

## 3. Проверка команд

`photo.add` и `photo.replace` получают необязательные `urls`, `width`, `height` и `deleteHandle`. Если поля нет, это значит `null`, поэтому старые команды остаются верными. `validateCommand` проверяет:
- **`urls`:** `null` или список из 1–8 копий.
  - У каждой копии `url` начинается с `https://` и не длиннее 2048 символов, иначе `invalid_url`.
  - `role` — строка длиной 1–40.
  - `width` и `height` — целые от 1 до 20000.
  - `fit` — `inside` или `cover`.
  - `type` — `null` или строка до 100 символов.
  - Любое другое нарушение даёт `invalid_option`.
- **`width` и `height`:** оба `null` или оба целые от 1 до 20000, иначе `invalid_option`.
- **`deleteHandle`:** `null` или строка длиной 1–2048, иначе `invalid_option`.

Проверку самого `url` этот план не меняет [решение Claude]. Защита от чужих адресов остаётся при показе: адрес хоста сверяется со списком разрешённых, и для каждой копии тоже.

## 4. База, резервные копии, кэш

- **Миграция `0002`** добавляет четыре колонки, все могут быть пустыми.
  - `min_app_schema` остаётся 3: приложение со схемой 4 читает и пишет базу со схемой 5 как раньше, потому что называет только свои колонки.
  - `APP_SCHEMA_VERSION` становится 5.
- **Вставка фото называет новые колонки только для полей, которые есть в команде.** Команда без них пишет ровно тот же запрос, что и схема 4 [решение Claude].
- **Чтение:** `urls` читается осторожно. Если в колонке не список, приложение считает её пустой (`null`).
- **Восстановление** получает тип колонки `jsonb`: значение едет как JSON-текст и превращается обратно в `::jsonb`.
- **Резервная копия:**
  - `version` остаётся 1.
  - Фото получает четыре поля, а для файлов старых схем они по умолчанию `null`.
  - Если `urls` в файле испорчен, весь файл отклоняется, как при любом другом испорченном поле.
- **Копия инвентаря на устройстве** сама перечитается при смене версии схемы (`FORMAT_MARK`).

## 5. Загрузка

- `prepareImage` возвращает `{ blob, width, height }`: итоговый размер после уменьшения до 2048.
- **Хостинг получает нейтральное имя файла:** `photo.webp` или `photo.jpg`, по типу сжатого файла. Название вещи и исходное имя (`IMG_1234.HEIC`) никуда не уходят [решение Claude]. Причина: у ImgBB имя становится публичным заголовком, а исходное имя ещё и с чужим расширением.
- **Ответ хранилища** (`StoredFile`) может содержать `urls` и `deleteHandle`. Команда получает всё это плюс `width` и `height`.

## 6. Показ

- Компоненты передают в показ фото целиком (`url` и `urls`), а не одну строку адреса. Это `PhotoImg`, миниатюра вещи и обложки в `views.ts`.
- **Выбор копии `pickRendition(urls, size)`.** Размеры: `thumb` 160, `card` 800, `full` 2048.
  1. Учитываются только копии с разрешённым хостом.
  2. Для `card` и `full` годятся только копии `fit: inside`. Для `thumb` годятся любые: миниатюры всегда обрезаются по рамке.
  3. «Достаточно большая» копия:
     - для `thumb` — с короткой стороной не меньше 160;
     - для `card` и `full` — с длинной стороной не меньше нужного.
  4. Из достаточно больших берётся самая маленькая по площади. Если таких нет, берётся самая большая из подходящих. Если подходящих нет вовсе, адрес строится из `url`, как сейчас.
- **Что это даёт для ImgBB:**
  - `thumb` — копия 180×180;
  - `card` — оригинал, потому что 640 меньше 800;
  - `full` — оригинал.
- **Список разрешённых хостов** пополняется `i.ibb.co`.
- **Метка для кэша.** Копию ImgBB, выбранную для `thumb`, приложение запрашивает с меткой `?antresol=thumb`. По ней service worker кладёт её в кэш миниатюр. ImgBB эту метку игнорирует (проверено). Метка ставится только хостам, у которых это проверено; сейчас это только ImgBB.
- **Размеры для разметки** (чтобы место под фото не прыгало) в этот план не входят: размеры только сохраняются.

## 7. Хранилище ImgBB

- **Пакет `@antresol/files-imgbb`.** Экспортирует `isImgbbUrl(url)` и `createImgbbStore({ apiKey, fetch?, timeoutMs? })`.
- **Загрузка:** `POST https://api.imgbb.com/1/upload?key=<ключ>`, multipart-поле `image`, без `expiration`.
- **Ответ** превращается в `StoredFile`:
  - `provider` — `'imgbb'`;
  - `fileId` — `data.id`;
  - `url` — `data.image.url` (или `data.url`, если первого нет);
  - `urls`:
    - оригинал: `inside`, размер из ответа;
    - `medium`, если он пришёл: `inside`, размер — оригинал, вписанный в 640;
    - `thumb`, если он пришёл: `cover`, 180×180;
    - `type` у каждой копии берётся из `mime`;
  - `deleteHandle` — `data.delete_url` или `null`.
- **Проверка адресов.** Подходящий адрес выглядит как `https://i.ibb.co/<id>/<файл>.<webp|jpg|jpeg|png|gif>`. Неверный адрес оригинала даёт ошибку `failed`. Копия с неверным адресом выбрасывается.
- **Ошибки** — как у Imgur:

  | Причина | Код |
  |---|---|
  | HTTP 400, 401, 403 | `rejected` |
  | HTTP 413 | `too_large` |
  | HTTP 429 и 5xx | `unavailable` |
  | Сеть или тайм-аут | `unavailable` |
  | Отмена | `failed` |
  | Нечитаемый ответ | `failed` |

  Текст ошибки никогда не содержит ключа или адреса запроса.
- **Настройки источника:**
  - `photoStore: 'imgbb'`, ключ хранится в `imgbbApiKey`;
  - выбор: Uploadcare, Cloudinary, ImgBB, плюс Imgur, если он уже выбран;
  - ссылка ведёт на https://api.imgbb.com/;
  - подсказка: «Sign in to ImgBB, open api.imgbb.com and press Get API key. Photos on ImgBB are open to anyone with the link.»;
  - ключ скрывается в диагностике, а его смена пересобирает хранилище.
- **Сеть и кэш:**
  - CSP: `connect-src https://api.imgbb.com` и `img-src https://i.ibb.co`;
  - `i.ibb.co` загружается с `crossorigin="anonymous"`;
  - service worker кладёт `i.ibb.co/…?antresol=thumb` в кэш миниатюр, а остальное с `i.ibb.co` — в кэш полных фото.

## 8. Не входит

- удаление фото с хостингов (ключ удаления только хранится);
- использование размеров для разметки;
- S3-совместимое хранилище, R2, Neon Object Storage;
- дозаполнение `urls` и размеров у старых фото;
- возврат Imgur в выбор.

## 9. Ограничения

- Ветка `photo-renditions` от `master`, в своей рабочей папке. Push в `master` — только по команде владельца.
- Без строк атрибуции в коммитах.
- Только pnpm.
- Секреты не печатаются. Ключ ImgBB для проверок берётся только из `ANTRESOL_IMGBB_TEST_KEY` в `.env.local` и не выводится.
- Свои dev-серверы — из своих рабочих папок. Порты 3000 и 3002 принадлежат владельцу.

## 10. Приёмка

1. Новый источник предлагает Uploadcare, Cloudinary и ImgBB.
2. Фото, загруженное в ImgBB:
   - показывается в списке миниатюрой 180;
   - открывается целиком в 2048;
   - в базе у него записаны `urls` (три копии), `width`/`height` и `delete_handle`.
3. У фото Uploadcare и Cloudinary записываются `width`/`height`, а показ не изменился.
4. Резервная копия со схемой 4 восстанавливается, новые поля пустые. Новая копия восстанавливается с `urls`.
5. Тесты соответствия на Neon проходят: `urls` возвращается списком через PGlite, neon-http и neon-ws.
6. `pnpm test`, `pnpm typecheck`, `pnpm lint` зелёные.
