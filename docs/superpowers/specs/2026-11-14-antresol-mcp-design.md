# Antresol — локальный MCP-сервер и теги в поступлениях: дизайн

Дата: 2026-11-14
Статус: обсуждено с владельцем в чате 2026-11-13 — 2026-11-14.

Пометка **[решение Claude]** — выбор Claude, а не владельца. Владелец может его оспорить. Всё остальное решено владельцем в обсуждении.

Опирается на спецификацию поступлений `docs/superpowers/specs/2026-11-13-antresol-intakes-design.md` (черновики в базе, `resolveIntake`, `saveIntakeDraft`, проведение только в приложении) и на П22 из `docs/superpowers/proposals/2026-11-11-overnight-review.md` (частично устарел: Inbox предложений заменён черновиками поступлений).

## 1. Зачем

Владелец хочет вносить пачки деталей через ИИ-ассистента на компьютере. Типичный случай — опись: десятки пакетиков сфотографированы на телефон, рядом стикер с количеством и линейка. Позже, за компьютером, ассистент смотрит фото, находит похожее в инвентаре и собирает **черновик поступления**. Человек открывает черновик в приложении, проверяет и проводит его сам.

Отсюда главное правило: **ассистент никогда не пишет в склад напрямую**. Всё, что он может записать, — черновики поступлений. Отдельного Inbox предложений нет: черновик поступления и есть Inbox.

Второе правило: **сервер не привязан к Claude**. Обязательно работает в Claude Desktop и Claude Code; другие программы с поддержкой локальных MCP-серверов (Cursor, VS Code, Codex CLI, Gemini CLI, LM Studio и т. п.) должны работать без доработок, если поддерживают стандартный MCP. Ничего специфичного для Claude в сервере нет.

Вместе с MCP делаем **теги у новых предметов в поступлениях** (решение владельца 2026-11-14): сейчас черновик их не хранит, и ни приложение, ни ассистент не могут поставить тег новому предмету из поступления.

## 2. Цели, не-цели, анти-цели

### Цели
1. Локальный MCP-сервер (stdio) поверх `core` и `storage-postgres`: чтение инвентаря и запись черновиков поступлений.
2. Полный, узкий, но универсальный набор инструментов (§5): обзор метаданных, поиск, карточка предмета, папка, поступления, правка черновиков, фото.
3. Фото из папки на компьютере: ассистент их видит, а сервер загружает их в хранилище фото источника и прикрепляет к строкам.
4. Установка в Claude Desktop двойным щелчком (`.mcpb`), в остальные программы — фрагментом настроек из README. Подключение — одной вставкой из приложения.
5. Сборка и выпуск через GitHub Actions в GitHub Releases.
6. Теги у новых предметов в черновике поступления: в ядре, в хранилище, в шторке строки приложения и в MCP.
7. В конце проекта — «промпт» MCP с инструкцией разбора пачки фото в черновик (аналог скилла, §8).

### Не-цели
- Проведение поступления из MCP. Проводит только человек в приложении.
- Удаление черновиков из MCP **[решение Claude]**. Убрать строку можно, удалить весь черновик — только в приложении.
- Любая другая запись: предметы, остатки, папки, атрибуты, теги, словари напрямую. Предметы, варианты, остатки и теги меняются только через черновик и его проведение.
- Загрузка фото с телефона прямо в черновик («неразобранные фото») — следующий шаг, требует доработки приложения.
- Удалённый (интернетный) MCP-сервер. Обычный ChatGPT и веб-клиенты, которым нужен сервер в интернете, не поддерживаются: это противоречит принципу «без своего сервера».
- Интерфейс внутри чата (MCP Apps), перетаскивание фото в окно чата.
- Разбор текста в атрибуты без ИИ (бэклог D6). Физические места хранения: «куда положить» — только папка в иерархии.
- Отдельная роль Postgres без `DELETE` из П22 **[решение Claude]**: у модели нет SQL-инструмента, она может только то, что дают инструменты.
- Теги у существующих предметов через поступление: строка-пополнение теги предмета не меняет.
- Новые папки и новые атрибуты из черновика (решение владельца 2026-11-14: на потом). Новый предмет черновика ссылается только на существующие папку и атрибуты. Если подходящих нет, ассистент кладёт предмет в ближайшую подходящую папку и говорит в чате, чего не хватило; папку или атрибут человек заводит в приложении.
- Заметка у строки поступления (решение владельца 2026-11-14: не нужна). Сомнения и своё мнение ассистент высказывает в чате. В заметку черновика уходит только то, что нужно сохранить на будущее.

### Анти-цели (провал, даже если работает)
- Ассистент меняет склад в обход черновика.
- Строка подключения или ключ хранилища фото попадают в чат, в ответ инструмента или в лог.
- MCP молча затирает правки человека в том же черновике.
- Заметный расход трафика Neon Free (5 ГБ/мес) или перезагрузка инвентаря на других устройствах из-за MCP.
- Дубли: MCP заводит новый предмет, когда такой уже есть, и никак об этом не сообщает.
- Особенности одного клиента, ломающие остальные.

## 3. Подключение и установка

### 3.1 Ключ подключения из приложения
- В настройках источника Neon появляется кнопка **«Connect AI»** **[решение Claude: название]**. Она открывает окно с коротким объяснением, кнопкой «Copy connection key» и ссылкой на страницу релиза и README.
- **Ключ подключения** — одна строка текста с теми же данными, что уже передаёт «Share» по QR (`SharedConnection` в `packages/app/app/lib/connection-share.ts`): имя источника, строка подключения, выбранное хранилище фото и его ключи. Формат: префикс с версией и закодированный JSON **[решение Claude]**, например `antresol-connect-v1:<base64url>`. Без шифрования: ключ вставляется только в поле настроек на этом же компьютере.
- Окно предупреждает, что ключ даёт полный доступ к базе, и его нельзя вставлять в чат.
- У демо-источника (PGlite в браузере) кнопки нет: до него внешняя программа не дотянется.
- Читать IndexedDB браузера из MCP нельзя и не нужно (обсуждено и отвергнуто). Шифрованное сопряжение по коду тоже отвергнуто: код и токен прошли бы через чат.

### 3.2 Настройки сервера
Сервер получает настройки из переменных окружения **[решение Claude: имена]**:
- `ANTRESOL_CONNECTION` — ключ подключения (обязательно);
- `ANTRESOL_PHOTOS_DIR` — папка для фото. По умолчанию — кроссплатформенно (требование владельца 2026-11-14): папка «Изображения» пользователя плюс `Antresol`, вычисленная средствами Node, а не зашитым путём **[решение Claude: какая папка]**: `~/Pictures/Antresol` на macOS, `%USERPROFILE%\Pictures\Antresol` на Windows, `$XDG_PICTURES_DIR/Antresol` на Linux (иначе `~/Pictures/Antresol`). Если папки нет, сервер создаёт её при первом обращении **[решение Claude]**. В `.mcpb` поле папки по умолчанию пустое, и тогда действует это же правило.

Без ключа или с испорченным ключом сервер всё равно запускается и на любой вызов отвечает понятной ошибкой «вставьте ключ из Settings → Connect AI», а не падает при старте.

### 3.3 Claude Desktop: `.mcpb`
- Пакет `.mcpb` с манифестом: поле «Antresol connection key» (секретное, `sensitive`, хранится в связке ключей ОС) и поле «Photos folder» (папка).
- Один пакет на все ОС, если это возможно (см. §7 про обработку фото).

### 3.4 Остальные программы
- В релиз кладётся ещё и обычная сборка сервера одним файлом для запуска через `node`.
- README: готовые фрагменты настроек для Claude Code (`claude mcp add …`), Cursor, VS Code и Codex CLI. Ключ — в переменной окружения.
- Вручную проверяются только Claude Desktop и Claude Code. Остальные — по README, без проверки.

## 4. Данные и синхронизация

- Сервер открывает базу так же, как приложение: `openPostgresStorage` с исполнителем Neon HTTP. Если схема базы новее, чем знает сервер (`readOnly`), чтение работает, а запись отвечает «обновите Antresol MCP» **[решение Claude]**.
- **Снимок инвентаря хранится в памяти сервера.** Перед вызовом инструмента сервер дёшево сверяет `rev` (не чаще раза в несколько секунд — выбор исполнителя) и перечитывает снимок, только если `rev` изменился. Инструмент `refresh` перечитывает принудительно. Черновики читаются через `listIntakes` и `intakesRev` так же.
- MCP не меняет `rev`: он пишет только черновики (`saveIntakeDraft`), а они меняют только `intakes_rev`. Устройства с открытым приложением инвентарь не перезагружают.
- **Объём ответа для модели.** Трафик Neon дешёвый, а окно контекста модели — нет: 1000 предметов с атрибутами — порядка 50–150 тысяч токенов. Поэтому весь инвентарь одним ответом не отдаётся. Метаданные (папки, атрибуты, теги, единицы) отдаются всегда целиком в обзоре; предметы — через поиск, папку и карточку. Ответы компактные: JSON без лишних полей, у длинных списков — предел и признак «есть ещё».

## 5. Инструменты

Все инструменты принимают необязательный `inventory` (id или имя). Если в источнике один инвентарь, берётся он **[решение Claude]**. Если несколько и инвентарь не указан — ошибка со списком инвентарей.

Имена инструментов и полей — выбор исполнителя; ниже — что каждый обязан уметь.

### 5.1 Чтение
- **`get_overview`** — то, что ассистенту нужно всегда, и вызывается первым:
  - список инвентарей с валютой;
  - дерево папок (id, путь, число предметов);
  - все атрибуты: id, имя, тип, единица, значения перечислений, правила чисел;
  - все теги;
  - единицы: стандартные и свои;
  - настроено ли хранилище фото и какая папка фото.

  Это инструмент, а не «ресурс» MCP: ресурсы многие клиенты сами не подгружают **[решение Claude]**.
- **`search`** — поиск ядра (`createSearch`), понимает номиналы («4k7» = 4.7 kΩ). Возвращает предметы и варианты: путь папки, значения осей, остаток.
- **`get_item`** — карточка: имя, описание, путь папки, единица, теги, атрибуты, оси, варианты со значениями и остатком, ссылки на фото (миниатюры), последние поступления с ценой и ссылкой на товар **[решение Claude: последние N]**.
- **`get_folder`** — подпапки и предметы папки с остатком. По id или по пути.
- **`list_intakes`** — черновики и проведённые поступления: шапка, автор, число строк, статус. С поиском по магазину и номеру заказа.
- **`get_intake`** — поступление целиком. У черновика к каждой строке приложен разбор `resolveIntake` (`add`, `newValue`, `newItem` или проблема с кодом), к новым предметам — предупреждение «похоже, такое уже есть» (та же логика, что жёлтая плашка в приложении, `duplicateWarning`) и «уже есть в этом поступлении».
- **`refresh`** — перечитать снимок и черновики.

### 5.2 Запись черновиков
- **Создать черновик** с шапкой (магазин, номер заказа, дата, заметка).
- **Поправить шапку.**
- **Добавить строки** — пачкой за один вызов. Строка: существующий предмет (и значения осей) или новый предмет черновика; количество; цена за строку; ссылка на товар; фото (путь к файлу). В том же вызове можно объявить новые предметы (имя, папка, единица, атрибуты и оси, теги) и сослаться на них из строк.
- **Поправить строку**, **убрать строку**, **поправить новый предмет** (имя, папка, единица, атрибуты, теги).
- Дописывать и править можно **любой черновик**, не только созданный MCP (решение владельца): понятия «черновик MCP» нет.

Правила записи:
- Значения — текстом, как их пишет человек, и разбираются ядром по тем же правилам, что в приложении: количество с единицей и приставкой, цена в валюте инвентаря (`parseMoneyText`, без float), значения атрибутов по правилам атрибута (`4k7`).
- Каждая запись: перечитать черновик из базы → внести правку → проверить через `resolveIntake` → записать через `saveIntakeDraft` с `baseDraftRev`. Строки с проблемами записываются (как в приложении), а ответ инструмента их перечисляет.
- **Конфликт.** Если черновик изменился между чтением и записью, сервер перечитывает и повторяет правку один раз; если снова конфликт — ответ «черновик сейчас правят в приложении», без `force` **[решение Claude]**. MCP никогда не пишет с `force`.
- Ответ на запись — черновик после записи в том же виде, что `get_intake` (с разбором и предупреждениями о дублях), чтобы ассистент сразу видел проблемы.
- Автор: `Actor.device` = имя программы, которое клиент сообщает при подключении (`clientInfo.name`), плюс « · MCP», например «Claude Desktop · MCP» **[решение Claude]**; если имени нет — «AI · MCP». Это заменяет жёсткое `Claude · MCP` из записей поступлений.

### 5.3 Фото
- **`list_photos`** — файлы изображений в папке фото (или в указанной папке): имя, размер, дата, и уже ли файл прикреплён к строке какого-то черновика.
- **`view_photo`** — возвращает уменьшенное изображение (стандартный тип содержимого MCP `image`), чтобы ассистент прочитал стикер, линейку и надписи. Размер — с учётом пределов клиентов на размер ответа **[решение исполнителя: точные числа]**. Можно попросить несколько фото за вызов.
- **Прикрепление**: путь к файлу в строке. Сервер готовит фото по тем же правилам, что приложение (`packages/app/app/lib/images.ts`: не больше 2048 px по длинной стороне, WebP или JPEG, HEIC с iPhone декодируется) и загружает его в хранилище фото источника (`defaultFileStore` и пакеты `files-*`).
- **Одна загрузка на файл.** Сервер помнит соответствие «содержимое файла → загруженный файл» в небольшом файле состояния на компьютере, чтобы повторное прикрепление того же фото не загружало его заново, и чтобы `list_photos` показывал «уже использовано».
- Файлы в папке сервер не двигает и не удаляет **[решение Claude]**.
- Без хранилища фото у источника строки без фото записываются, а попытка прикрепить фото даёт понятную ошибку.
- Пути только локальные: сервер читает любой путь, который ему передали, с правами пользователя. Отдельный доступ к файловой системе не нужен. Фото, вложенные прямо в чат, до сервера не доходят (ограничение MCP-клиентов, проверено 2026-11-14) — это объясняется в README.

## 6. Теги в поступлениях

- У нового предмета черновика (`DraftNewItem`) появляются теги: **существующие по id и новые по имени** **[решение Claude]**. Новый тег создаётся при проведении, в той же атомарной записи; если к этому моменту тег с таким именем уже есть (без учёта регистра), берётся он.
- Черновики, сохранённые до этой правки, читаются как «без тегов». Старые резервные копии восстанавливаются.
- **Шторка строки** (состояние 4, новый предмет): выбор тегов, как в форме предмета (`ItemForm.vue`), свёрнутый в строку-сводку по принципам шторки. «+ Add tag» в шторке не создаёт тег сразу, а кладёт имя в черновик **[решение Claude]** — так набор черновика по-прежнему не меняет `rev`.
- **Проведение** (`intake.commit`, `buildIntakeCommit`): новые предметы получают теги; новые теги создаются до предметов.
- Правка нового предмета из любой его строки меняет и теги общего предмета, как сейчас имя и атрибуты.
- MCP пишет теги тем же форматом черновика.

## 7. Код, сборка и выпуск

- **Где работаем** (решение владельца 2026-11-14): отдельный worktree. Ветка `mcp` **[решение Claude: имя]** от текущего локального `master` (там уже поступления, `1cbe7f1`, схема 6, ещё не запушены). План заканчивается на «готово к выпуску»: слияние, пуш (он же выкладывает приложение на Pages и переводит живую базу на схему 6 при следующем открытии), тег и релиз — только по отдельной команде владельца.

- Новый пакет `packages/mcp` (`@antresol/mcp`) на официальном TypeScript SDK MCP, транспорт stdio.
- Логика, которую сейчас держит приложение и которая нужна серверу, переезжает в общие пакеты, а не копируется **[решение Claude]**: например, `duplicateWarning` и сопутствующее из `packages/app/app/lib/intake-line.ts`, выбор хранилища фото из `defaultFileStore`, разбор ключа подключения. Куда именно — выбор исполнителя.
- **Обработка фото в Node.** Браузерный canvas недоступен. Нужна библиотека изображений, которая работает на macOS, Windows и Linux внутри одного `.mcpb`. Предпочтение — решения на WASM без платформенных бинарников; выбор исполнителя, если один пакет на все ОС соблюдён. Если без платформенных сборок не обойтись — по `.mcpb` на ОС.
- Сборка в один файл; Node — та версия, которую `.mcpb` гарантирует в Claude Desktop (исполнитель проверяет).
- **GitHub Actions:** по тегу вида `mcp-v*` **[решение Claude]** — тесты, сборка, упаковка `.mcpb`, загрузка `.mcpb` и однофайловой сборки в GitHub Release. Пуш и создание тега — только по команде владельца.
- **README**: установка в Claude Desktop, фрагменты для других программ, где взять ключ, что умеет сервер, что фото из чата не доходят.

## 8. Промпт разбора фото (в конце проекта)

- MCP-«промпт» (стандартная часть MCP) — инструкция ассистенту: как разобрать пачку фото в черновик. Например: начать с `get_overview`; читать количество со стикера и размеры по линейке; для каждого пакетика искать похожее (`search`); предпочитать пополнение и новый вариант существующего предмета новому предмету; не угадывать — сомнительное называть в чате (заметки у строки нет), а в заметку черновика писать только то, что стоит сохранить на будущее; в конце показать сводку и напомнить, что проводить в приложении.
- Не все клиенты показывают промпты; поэтому краткая версия тех же правил живёт ещё и в описаниях инструментов и в `instructions` сервера, чтобы работало и без промпта **[решение Claude]**.
- Текст промпта согласуется с владельцем после пробы на настоящих фото.

## 9. Как проверяем

- Обработчики инструментов — тестами против PGlite в памяти (как тесты хранилища) и поддельного хранилища фото, без сети.
- Протокол — через транспорт SDK в памяти: список инструментов, вызовы, ошибки.
- Теги в поступлениях — тесты ядра и хранилища, набор соответствия Neon по правилам репозитория (только база `_test`).
- Вручную: Claude Desktop с `.mcpb` и Claude Code — подключение ключом, обзор, поиск, черновик из 3–5 фото, проверка и проведение в приложении.
