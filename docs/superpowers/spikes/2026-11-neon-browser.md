# Спайк: Neon из браузера (2026-11-10)

Цель: проверить, что приложение без сервера может ходить в Neon прямо из браузера, на компьютере и на Android-телефоне, и выбрать основной драйвер для плана 2.

Код спайка: `spikes/neon-browser`. Это страница на Vite без фреймворка. Она прогоняет четыре сценария на тестовой базе `graymatter_test` и выводит время каждого шага:

- **HTTP raw.** `neon(url)`: `select 1` дважды, `CREATE TABLE`, `sql.transaction` с двумя `INSERT`, `count(*)`, `DELETE`.
- **WebSocket raw.** `Pool`: `connect`, `select 1`, `CREATE TABLE`, `BEGIN`, два `INSERT`, `COMMIT`, `count(*)`, `DROP TABLE`.
- **GrayMatter storage (websocket / http).** Сверх плана: наш настоящий `@graymatter/storage-postgres` в браузерной сборке. Шаги: `openPostgresStorage` (миграции через `import.meta.glob`), `apply(inventory.create)`, `listInventories`, `loadInventory`.

Проект Neon: `graymatter`, регион aws-eu-central-1 (Франкфурт).

## Результаты

### Компьютер: Chrome 157, macOS

Все шаги прошли, в консоли нет ошибок и предупреждений драйвера. Время в мс:

| Шаг | Прогон 1 | Прогон 2 |
|---|---|---|
| HTTP `select 1`, первый | 1177 | 60 |
| HTTP `select 1`, повторный | 142 | 325 |
| HTTP `sql.transaction`, 2 `INSERT` | 63 | 55 |
| HTTP `count(*)` | 94 | 56 |
| WS `connect` | 288 | 247 |
| WS один запрос (`select 1` / `INSERT` / `COMMIT`) | 50–140 | 50–130 |
| Storage WS: `open` (миграции / проверка схемы) | 527 | 452 |

1177 мс в первом прогоне — это пробуждение уснувшего compute Neon. Повторный запрос занимает 50–150 мс.

### Телефон: Chrome на Android

Владелец сообщил, что все четыре сценария прошли. Время не сохранилось: результаты отправлялись на экземпляр dev-сервера, который потом перезапустили.

По Wi-Fi страница с телефона не открылась: `ERR_TOO_MANY_RETRIES` по адресу `http://192.168.1.127:5173`. При этом сервер слушал все интерфейсы, файрвол macOS был выключен, а с самого Mac страница по этому адресу отвечала. Вероятная причина — VPN на телефоне или изоляция клиентов в Wi-Fi. Причину не выясняли.

Сработал USB: `adb reverse tcp:5173 tcp:5173`, затем на телефоне `http://localhost:5173/?k=<токен>`.

## Выводы

1. **Браузер ходит в Neon напрямую через оба драйвера, на компьютере и на телефоне.** Сервер приложению не нужен. Наш пакет хранилища целиком, вместе с мигратором, работает в браузерной сборке.
2. **HTTP выполняет нашу команду за один запрос.** Каждая команда у нас — один атомарный пакет без чтения перед записью, и `sql.transaction` отправляет весь пакет одним HTTP-запросом: ~50–60 мс. WS тратит отдельный обмен с сервером на `BEGIN`, на каждый оператор и на `COMMIT`, плюс ~250 мс на подключение: 140–210 мс даже на маленькой команде.
3. **WS медленно загружает инвентарь: ~1,1 с против ~120 мс у HTTP.** `loadInventory` шлёт 11 запросов параллельно, и `Pool` открывает под них отдельные WebSocket-соединения.
4. **HTTP не держит соединение.** На телефоне это важно: при смене сети и в фоновой вкладке нечему обрываться.

## Решение

**Основной драйвер — HTTP** (`createNeonHttpExecutor`).

План говорил: брать WebSocket, если он работает на телефоне. WebSocket на телефоне работает, но на нашей модели доступа HTTP быстрее и проще: команды — это неинтерактивные пакеты, загрузка — это параллельные чтения. WS-исполнитель остаётся в пакете и в тестах на реальном Neon. Он пригодится, если появятся интерактивные транзакции.

## Что это меняет в плане 2

- Экран «Источники» подключает Neon через HTTP-исполнитель.
- `loadInventory` стоит собрать в один `sql.transaction` только на чтение с изоляцией `RepeatableRead`. Это один запрос и согласованный снимок. Сейчас это 11 отдельных запросов.
- На телефоне проверять через `adb reverse tcp:5173 tcp:5173` и `http://localhost:5173`. Доступ по локальной сети у владельца не работает. К тому же `localhost` считается безопасным контекстом, а он нужен PWA и service worker.
